# Измерения 0.9 против 0.6

Локальная Windows x64, одинаковые версии и файлы движков, CPU-кодирование видео, сбалансированный режим (2 потока). Три чередующихся запуска каждой версии; медианы. Короткие синтетические файлы, прогретый кэш. Это проверка накладных расходов, а не обещание скорости на больших пользовательских файлах. Команда: `python scripts/benchmark.py`; исходные результаты: [JSON](performance-0.9.json).

Базовые ZIP и EXE 0.6 проверены по SHA-256 до запуска. Хеши входов сохранены; оригиналы не изменились. Результаты совпали побайтно, кроме DOCX→PDF: там проверены текст и число страниц (метаданные времени генерации могут отличаться).

| Сценарий | Время 0.6 / 0.9, мс | CPU всего дерева, мс | Пиковая сумма RSS, МиБ | Размер результата, байт |
|---|---:|---:|---:|---:|
| PNG→JPEG, 1600×1000 | 23,0 / 22,9 | 15,6 / 31,3 | 10,9 / 10,7 | 218130 |
| MP4→MP4 H.264, 4 с 720p | 763,7 / 765,4 | 1609,4 / 1734,4 | 203,6 / 204,8 | 1444000 |
| WAV→FLAC, 10 с | 75,6 / 76,9 | 78,1 / 78,1 | 33,1 / 30,2 | 129190 |
| DOCX→PDF | 5420,6 / 5487,8 | 5078,1 / 4921,9 | 501,3 / 501,9 | 30702 |
| Текстовый PDF→TXT | 13,3 / 14,7 | 15,6 / 15,6 | 8,5 / 9,7 | 37 |
| Скан PDF→TXT OCR | 397,1 / 397,1 | 390,6 / 390,6 | 105,6 / 105,7 | 32 |

CPU учитывается Windows Job Object вместе с дочерними процессами. Сумма RSS опрашивается каждые 5 мс: короткие пики можно пропустить, общие страницы разных процессов могут учитываться несколько раз. Отдельно JSON содержит пик commit всего Job Object; это не RSS. Дискретность учёта CPU и короткие сценарии ограничивают точность. Видеотест показал больше CPU при близком времени; вывод об ускорении или экономии CPU по этим данным не делается.

Простой измерялся отдельно, без конвертаций и сети, по 15 секунд в новых копиях, с выключенными автообновлениями. Обе версии накопили 0,0 мс CPU в интервале; working set 16,3 МиБ у 0.6 и 16,6 МиБ у 0.9. Тест завершил только собственные процессы. Короткий замер не заменяет длительного наблюдения.

Базовый ZIP — около 0,5 МБ, установщик — около 2,5 МБ. Полные размеры и итоговые хеши записываются в приёмку выпуска. Основной выигрыш — отсутствие ненужных движков в базовом дистрибутиве; сами движки не заменялись. Из-за нагрузки Office и отсутствия доказанного выигрыша параллельная очередь не добавлена. Экономный режим остаётся последовательным с одним потоком движка, сбалансированный — с двумя.
