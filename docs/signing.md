# Подпись обновлений и подготовка CI — 0.8

Перед сборкой актуального выпуска выполните `python tests/release_config_tests.py`:
он проверяет согласованность текущих версий, включая defaults workflow и генератора манифеста.
Workflow выполняет эту проверку автоматически до bootstrap/подписания.
Статус локальной подготовки0.14 и открытые внешние проверки: [отчёт](release-readiness-0.14.0.md).

Настоящих ключей и сертификата владелец пока не предоставил. Обычная локальная
сборка НЕ имеет активной проверки подписи манифеста и продолжает прежний HTTPS +
SHA256 канал0.7. Эта подготовка не считается включённой цифровой подписью.

## Подключение ключа манифеста

Используется ECDSA P-256 / SHA256, подпись64 байта P1363 (r||s). Публичный ключ —
BCRYPT_ECCPUBLIC_BLOB72 байта (ECS1, cbKey32, координатыX/Y),144 hex-символа.
Секретный ключ PKCS8 PEM хранится у владельца или в секретах CI, не в Git.
Скрипт `scripts/sign-update-manifest.ps1` требует PowerShell7.2+, сверяет
публичную часть ключа с pin-файлом и подписывает точные UTF-8/LF байты.

При конфигурации CMake задаются `SHIFTWHEEL_UPDATE_PUBLIC_KEY` и
`SHIFTWHEEL_UPDATE_KEY_ID`. Они встраиваются в EXE; ключ не загружается с сервера.
С такой сборкой неподписанный, повреждённый, подписанный другим ключом/ID или
более старый, чем приложение, манифест отклоняется. Приложение дополнительно
помнит наибольшую принятую версию между запусками. Это защита от сетевого
отката; локальный владелец профиля может изменить/удалить состояние.

Подпись охватывает `ShiftWheel-update-v1\nkey_id=<ID>\n` + исходный манифест
с завершающим LF. К нему добавляются строки `key_id=` и `signature=` (128hex).
Нативная проверка: `build/Release/signature_tests.exe MANIFEST PUBLIC_HEX KEY_ID MIN_VERSION`.
Проверен реальный обмен PowerShell/.NET→C++/BCrypt на временных тестовых ключах.
Тестовые приватные ключи удаляются и в продукт не включаются.

Закреплённая сборка использует `updates/stable-signed.txt`; стандартный GitHub
адрес старого `stable.txt` переключается на подписанный адрес в памяти.
Пользовательский канал должен поставлять тот же подписанный формат. Старые
клиенты0.7 продолжают получать четырёхстрочный `stable.txt`.

Смена ключа выполняется отдельным подписанным выпуском, доставленным через
старый доверенный ключ, и обновлением закреплённого ключа в следующем EXE.
Для ещё не обновившихся клиентов нужно сохранять отдельный канал под старым
ключом либо обеспечить ручной переход; автоматическая двухключевая ротация
не реализована. Автоматическое доверие новому ключу из манифеста не поддерживается. Для отзыва
компрометированного ключа нужен отдельно доверенный канал доставки/ручная установка.

## Authenticode и выпуск

`scripts/sign-windows.ps1` подписывает EXE/установщик сертификатом Code Signing
из CurrentUser/My, проверяет срок, приватный ключ и результат Authenticode.
Настоящая подпись и timestamp не выполнялись: сертификата нет.

Workflow `.github/workflows/release.yml` запускается вручную, environment `release`.
В variables: `UPDATE_PUBLIC_KEY_HEX`, `UPDATE_KEY_ID`. В secrets:
`UPDATE_SIGNING_KEY_PEM`, `CODE_SIGN_PFX_BASE64`, `CODE_SIGN_PFX_PASSWORD`.
Сертификат/секретные файлы существуют только в одноразовом runner и удаляются;
они не входят в пакеты/артефакты. Настройте required reviewers для environment.

Workflow проверяет конфигурацию, скачивает движки из проверенного SHA256 ZIP0.7,
собирает и запускает все тесты, подписывает EXE, пакует ZIP и установщик,
подписывает установщик, затем вычисляет итоговые хеши и подписывает манифест.
Нативный verifier проверяет результат. `publish=false` выполняет подготовку;
`publish=true` разрешён только из main. Публикуются сначала все проверенные
пакеты/хеши/манифесты, проверяется публичная доступность, затем каналы.
Если выпуск уже существует, сценарий останавливается для проверки черновика,
а не заменяет его файлы. Ошибка не даёт опубликовать канал раньше пакетов.

Workflow пока не выполнялся на GitHub: это подготовленное подключение, а не
подтверждённый выпуск с реальными ключами. Нужны первая проверка в CI и отдельная
Windows VM для обновления/входа в систему. Докачка HTTP Range не добавлена:
используется полная потоковая загрузка с итоговой проверкой размера и SHA256.
